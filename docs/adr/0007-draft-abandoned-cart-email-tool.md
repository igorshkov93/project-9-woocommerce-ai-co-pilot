# ADR 0007: draft_abandoned_cart_email tool

## Status
Accepted

## Context

Step 14 responds to "Напиши email-кампанию для брошенных корзин". Unlike
Steps 9-13, this tool's output is generated by an LLM (Claude Haiku) rather
than aggregated/transformed from deterministic data, and it does not
mutate any external system - the result is a text draft returned to the
owner in Telegram, not a sent email.

Probed 2026-08-27: GET /wp-json/copilot/v1/abandoned-carts returns
`{ generated_at_gmt, generated_at_local, timezone, threshold_minutes,
store_currency, count, carts: [...] }`. Each cart:
`{ id, email, first_name, items_count, cart_total, currency,
items: [{ product_id, sku, name, quantity, price, line_total }],
created_gmt, updated_gmt, updated_local, minutes_since_update,
recovered, recovered_order_id }`. Current data: 5 unrecovered carts,
$79-$289, 1-3 line items each.

## Decisions

### 1. Target cart selection

The tool does not take a cart identifier as input (no natural-language
entity to resolve via Step 10 - the ТЗ command names no customer). It
auto-selects the single highest-value cart among those with
`recovered == false`: highest `cart_total`, ties broken by lowest
`minutes_since_update` (more recently abandoned = better recovery odds).
Currently resolves to cart id=4 (Dmytro, $289).

`no_data` status when the filtered (non-recovered) cart list is empty.

Drafting one email for the whole list ("real campaign") is out of scope
for this step - it multiplies LLM cost per invocation and complicates the
Telegram reply. Can be added later as a batch mode without changing this
contract.

### 2. Single-phase contract, no Telegram confirmation

Nothing is sent or mutated - the output is a draft the owner reads and
decides what to do with. This tool has the same shape as ADR 0004/0005's
read tools (`ok | no_data | invalid_input | upstream_error`), not the
propose/confirm shape from ADR 0006. `invalid_input` is effectively unused
today (the tool takes no meaningful input) but kept in the contract for
consistency and future parameters (e.g. an explicit cart id override).

### 3. No coupon integration in this tool

The email does not offer a discount code. Chaining `create_coupon` +
`draft_abandoned_cart_email` into one owner-facing action is left to the
Step 15 Agent, which can call both tools if it judges a discount is
warranted. Keeps this sub-workflow single-responsibility, consistent with
Steps 9-13.

### 4. No fabricated claims

The system prompt explicitly restricts the model to facts present in the
API response: product names, quantities, prices, cart total, currency,
first name. It is instructed NOT to invent urgency claims not backed by
data - no "only 2 left in stock", no discount percentages, no delivery
deadlines. This is a correctness/trust requirement, not a style
preference: a fabricated scarcity claim in a real business email is a
liability, and getting this wrong would be an obvious flaw to an
interviewer reading the workflow.

### 5. Model and cost

`claude-haiku-4-5-20251001` (pinned snapshot, not the rolling alias, for
reproducible behavior). $1/MTok input, $5/MTok output. A single call
(cart data + system prompt as input, ~300-token email as output) costs
roughly $0.003-0.006 - negligible against the ~$8.72 budget even across
many test iterations during development.

### 6. Output contract

```json
{
  "status": "ok",
  "cart": { "id": 4, "email": "dmytro.b@example.com", "first_name": "Dmytro", "cart_total": 289, "currency": "USD" },
  "subject": "...",
  "body": "..."
}
```

### 7. Verification methodology differs from prior tools

Steps 11-13's verify scripts asserted exact values (money to the cent,
deterministic coupon codes). LLM output is non-deterministic, so
`verify_draft_abandoned_cart_email.py` instead asserts structural/content
properties: valid JSON shape, non-empty subject/body within sane length
bounds, at least one real product name from the target cart appears
verbatim in the body, no unfilled template placeholders, and no digit
sequence resembling a discount percentage (a cheap proxy check against
the "no fabricated discount" rule) unless explicitly allowed.

## Consequences

- Selecting "highest value, non-recovered" is a simple, defensible
  heuristic but not personalization-optimal (e.g. ignores how close the
  customer might be to converting). Acceptable for a portfolio demo;
  worth flagging as a future refinement.
- Verification can catch structural regressions and factual drift (wrong
  product name, missing data) but cannot fully guarantee prose quality -
  a human read-through before using real output remains valuable, same as
  any LLM-generated business copy.

  
## Addendum (2026-08-27, post n8n integration)

- Discovered during 14.5: docker-compose.yml's `n8n` service environment
  block did not forward `COPILOT_API_BASE`, `WP_APP_USER`,
  `WP_APP_PASSWORD`, or `ANTHROPIC_API_KEY` into the container. Every
  prior workflow (09-13) only needed WooCommerce REST vars, which were
  already forwarded, so this gap went unnoticed until this tool needed
  WP Application Password auth and the Anthropic API key from `$env`
  inside a Code node. Fixed by adding all four to the `environment:`
  block and recreating the container (`docker compose -f
  docker\docker-compose.yml --env-file .env up -d`).
- End-to-end verified: `14-tool-draft-abandoned-cart-email` (id
  `qcjOmx2r0K6bTmP2`), 12 nodes, matches the Python reference on cart
  selection (id=4, Dmytro, $289) and produces a grounded, non-fabricated
  email via a live Claude Haiku call.
